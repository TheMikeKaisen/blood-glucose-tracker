## 📌 Critical Findings of the App Until Now

1. **Domain & Clinical Requirements:**
   - Designed for diabetes patients to record up to 4 readings per day across four chronological meal slots:
     1. `morning_fasting` ("Morning (fasting)")
     2. `after_breakfast` ("After breakfast")
     3. `after_lunch` ("After lunch")
     4. `after_dinner` ("After dinner")
   - Clinical target guidelines (ADA): Low (< 70 mg/dL), In-target / Normal (70–99 fasting, < 140 post-meal), Borderline (100–125 fasting, 140–180 post-meal), High (≥ 126 fasting, > 180 post-meal).
   - "Clinical Calm" UI/UX: high whitespace, calm colors (sage greens, slate blues, warm ochre, muted crimson), high WCAG 2.2 AA contrast, accessible typography.
2. **Date & Timezone Integrity:**
   - Storing dates with UTC conversion shifts days across midnight (e.g., 11:30 PM local shifting to yesterday in UTC).
   - All glucose readings are stored strictly as ISO calendar date strings (`YYYY-MM-DD`) mapped to PostgreSQL `DATE` types.
   - Future date checks compare client calendar date without timezone shifts.
3. **Exact Error Validation Parity:**
   - Error messages must match the exact specification from `Assignment.md`:
     * Missing value: `"Please enter a glucose value."` (HTTP 422)
     * Out of range / non-integer: `"Value must be between 40 and 600 mg/dl."` (HTTP 422)
     * Duplicate slot: `"You already have an {Slot Name} reading for this date."` (HTTP 409)
     * Exceeded daily count: `"You can add only 4 readings per day."` (HTTP 409)
     * Future date: `"Date cannot be in the future."` (HTTP 422)
4. **Data Isolation & IDOR Prevention:**
   - Strict multi-tenant isolation enforced at the database level: every reading query includes `WHERE user_id = $1`.
   - Edits and deletes must verify user ownership before mutating records.
5. **Database Strategy:**
   - Local development uses a Docker PostgreSQL container.
   - Designed for zero-code portability to Supabase by simply switching `DATABASE_URL`.
   - All primary keys use modern standard `BIGINT GENERATED BY DEFAULT AS IDENTITY`.

## 💻 Tech Stack

- **Backend Runtime & Framework:** Node.js (v20+ / v22+), Express (CommonJS for seamless Jest and supertest compatibility).
- **Database:** PostgreSQL (v16), accessed via `pg` (node-postgres connection pool). Docker container locally; Supabase ready.
- **Authentication & Security:**
  - Password hashing: `argon2` (Argon2id profile, OWASP recommended).
  - Tokens: JSON Web Tokens (`jsonwebtoken`) with strict HMAC SHA-256 verification (HS256, issuer: `sweety-api`, audience: `sweety-client`).
  - Storage: Short-lived access tokens (5–10 min) in httpOnly, Secure, SameSite cookies. Refresh tokens stored as SHA-256 hashes in PostgreSQL.
  - CSRF: Double Submit Cookie pattern (`X-CSRF-Token` header matched against signed/verified cookie).
  - Security Headers: `helmet`.
  - Rate Limiting: `express-rate-limit`.
  - Cookies: `cookie-parser`.
- **Validation:** `zod` for request boundary validation (schemas for body, params, query).
- **Frontend (Upcoming):** React 18 / 19, Vite, TypeScript, Tailwind CSS, Lucide React, Recharts.
- **Testing:** Jest, Supertest.

## 🛡️ Security Requirements

1. **Cookie-Based JWT Access Tokens:**
   - Access tokens are stored solely in `httpOnly`, `Secure` (in production/HTTPS), `SameSite=Lax` cookies.
   - Tokens are **never** returned in JSON response bodies or stored in `localStorage` or `sessionStorage` (preventing XSS exfiltration).
2. **Cryptographic Refresh Token Rotation:**
   - Opaque 256-bit cryptographically secure random tokens (`crypto.randomBytes(32).toString('hex')`).
   - Plaintext refresh tokens are never persisted in the database; only SHA-256 hashes (`token_hash`) are stored.
   - On every `/api/auth/refresh`, the presented refresh token is invalidated and a fresh one is issued (Rotation).
   - **Reuse Detection:** If an already-revoked refresh token is presented, the system triggers compromise detection and revokes ALL active sessions for that user.
3. **Session Revocation & Logout:**
   - `/api/auth/logout` immediately invalidates the active refresh token and clears client cookies.
   - `/api/auth/logout-all` revokes all active refresh tokens for the user across all devices.
4. **CSRF Protection:**
   - State-changing requests (`POST`, `PUT`, `DELETE`, `PATCH`) must include an `X-CSRF-Token` header matching the issued CSRF token cookie.
5. **CORS:**
   - Explicit origin allowlist (default `http://localhost:5173`), `credentials: true`. Wildcards (`*`) are strictly forbidden.
6. **Strict JWT Verification:**
   - Enforce `algorithms: ['HS256']`, `issuer: 'sweety-api'`, `audience: 'sweety-client'`, and expiration.
7. **No Sensitive Information Disclosure:**
   - Error responses in production must never reveal stack traces, SQL syntax, or database internals.
   - Generic sanitized error messages returned to clients: `{ "error": "Internal server error" }`.

## 🧪 Testing Requirements

1. **Native Test-Driven Development (TDD):**
   - Follow Red-Green-Refactor.
   - Write failing integration tests first (`tests/auth.test.js`, etc.), verify failure, implement code, verify green.
2. **Comprehensive Integration Testing:**
   - Use `supertest` against the Express `app` without binding to physical network ports.
   - Cover happy paths, input validation failures, authentication/authorization failures, token expiry/tampering, rate limiting, and CSRF protection.
   - Never weaken or skip tests to make changes pass.
