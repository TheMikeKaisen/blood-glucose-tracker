# 📋 Sweety – Architectural Decision Records (ADRs)

This document records the architectural and technical decisions made for the Sweety project, along with context, alternatives considered, and consequences.

---

## ADR-001: Password Hashing with Argon2id

- **Status:** Accepted
- **Context:** `Assignment.md` mentioned bcrypt for password hashing. However, modern cryptographic standards (OWASP, IETF RFC 9106) recognize Argon2id as superior due to memory-hardness that defends against GPU/ASIC acceleration, and resistance to side-channel timing attacks.
- **Decision:** Use `argon2` (Argon2id profile) for all user password hashing and verification.
- **Consequences:**
  - Dramatically improves resistance against offline brute force attacks if database credentials are breached.
  - Requires native bindings (`node-addon-api`/`node-gyp-build`), which are available and tested for modern Node runtimes.

## ADR-002: httpOnly Cookies + Opaque Refresh Token Rotation vs localStorage

- **Status:** Accepted
- **Context:** Storing JWT tokens in browser `localStorage` or `sessionStorage` exposes tokens to Cross-Site Scripting (XSS) exfiltration. Returning tokens in JSON response bodies encourages unsafe frontend storage.
- **Decision:**
  1. Access tokens are stored solely in short-lived (10-minute) `httpOnly`, `Secure` (in production), `SameSite=Lax` cookies.
  2. Tokens are never returned in JSON response bodies.
  3. Refresh tokens are 256-bit opaque random hex strings stored in an `httpOnly` cookie.
  4. Only SHA-256 hashes of refresh tokens are stored in the database.
  5. Tokens are rotated on every exchange (`/api/auth/refresh`). If an already-revoked refresh token is presented, all sessions for that user are immediately revoked (Reuse Detection).
- **Consequences:**
  - Eliminates token theft via XSS.
  - Requires CSRF defense because browser cookies are ambient credentials sent automatically.

## ADR-003: Double Submit Cookie Pattern for CSRF Protection

- **Status:** Accepted
- **Context:** Because authentication relies on cookies, state-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) are susceptible to Cross-Site Request Forgery unless defended.
- **Decision:** Implement the Double Submit Cookie pattern:
  - An accessible `csrfToken` cookie is issued to the client.
  - Any mutating request must pass the matching value in the `X-CSRF-Token` HTTP header.
  - State-changing requests without a valid matching header are rejected with `403 Forbidden: "Invalid or missing CSRF token"`.
- **Consequences:**
  - Third-party domains cannot read the CSRF cookie due to the Same-Origin Policy and cannot construct the custom header.
  - Frontend client must attach the header to mutation requests.

## ADR-004: Primary Keys using `BIGINT GENERATED BY DEFAULT AS IDENTITY`

- **Status:** Accepted
- **Context:** PostgreSQL legacy `SERIAL` types create implicit sequences with quirks and are deprecated in SQL:2003 standards. Supabase and modern PostgreSQL standards recommend `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- **Decision:** Use `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` across all tables (`users`, `refresh_tokens`, `readings`).
- **Consequences:**
  - Full compatibility between local PostgreSQL Docker containers and Supabase.
  - Prevents integer overflow issues that affect standard 32-bit `SERIAL` IDs.

## ADR-005: Strict JWT Claim Verification

- **Status:** Accepted
- **Context:** Misconfigured JWT libraries can accept unsigned tokens (`algorithm: "none"`) or tokens minted by other services if claims are not strictly validated.
- **Decision:**
  - Token signing explicitly specifies `algorithm: 'HS256'`, `issuer: 'sweety-api'`, `audience: 'sweety-client'`, and `expiresIn: '10m'`.
  - Token verification strictly enforces `algorithms: ['HS256']`, `issuer: 'sweety-api'`, `audience: 'sweety-client'`.
- **Consequences:**
  - Completely eliminates algorithm switching and issuer spoofing attacks.

## ADR-006: Zod Boundary Validation

- **Status:** Accepted
- **Context:** Hand-crafted validation in Express controllers is error-prone, violates DRY, and leaks inconsistent error schemas.
- **Decision:** Use Zod schemas with a reusable Express middleware `validate(schema)` that inspects `req.body`, `req.query`, and `req.params`.
- **Consequences:**
  - Clear contract definitions for input payloads.
  - Exact verbatim error message enforcement matching assignment requirements.

---

## ADR-007: Port-Free Test Architecture via Supertest & App Export

- **Status:** Accepted
- **Context:** Binding Express directly to a network port during tests causes port collisions in parallel runs and slow teardown.
- **Decision:** Export `app` from `src/app.js` and isolate network listening in `src/server.js`. Tests invoke `supertest(app)`.
- **Consequences:**
  - Fast, reliable, port-free test execution.
  - Easy environment isolation during CI/CD.

## ADR-008: Atomic Refresh Token Rotation & Concurrency Defense

- **Status:** Accepted
- **Context:** Concurrent calls to `/api/auth/refresh` using the same valid refresh token could read `revoked_at IS NULL` simultaneously, resulting in double token issuance and bypassing breach detection.
- **Decision:** Revoke the refresh token atomically via `UPDATE refresh_tokens SET revoked_at = CURRENT_TIMESTAMP, replaced_by_token_hash = $1 WHERE id = $2 AND revoked_at IS NULL RETURNING id;`. If `rowCount === 0`, concurrent reuse is immediately flagged, triggering emergency revocation of all user sessions.
- **Consequences:**
  - Eliminates token proliferation and race-condition vulnerabilities.
  - Guarantees strictly linear token lineages.

## ADR-009: RFC 6265bis Cookie Clearance Policy

- **Status:** Accepted
- **Context:** RFC 6265bis mandates that cookies set with the `Secure` flag must also include the `Secure` flag when being cleared. Omitting flags causes browsers to ignore `Set-Cookie: token=; Path=/; Expires=Thu, 01 Jan 1970` directives.
- **Decision:** Define explicit cookie clearance constants matching the `path`, `secure`, and `sameSite` parameters used during cookie issuance.
- **Consequences:**
  - Guarantees reliable session termination across modern browser engines.

## ADR-010: Reverse Proxy Trust Configuration for Accurate Rate Limiting

- **Status:** Accepted
- **Context:** When running inside Docker containers or behind reverse proxies (Nginx, cloud load balancers), Express reads client IP from the direct TCP connection (the internal gateway IP), causing all users to share a single rate limiter bucket and risking denial of service.
- **Decision:** Configure `app.set('trust proxy', 1)` when in production or when `TRUST_PROXY` is enabled.
- **Consequences:**
  - Accurately tracks per-client IPs via `X-Forwarded-For`.
  - Prevents benign users from being blocked by neighbors behind proxies.

## ADR-011: Client Cookie Invalidation on Expired Refresh Tokens

- **Status:** Accepted
- **Context:** When `/api/auth/refresh` received an expired refresh token, it returned `401 Unauthorized` without calling `clearAuthCookies()`, causing clients to repeatedly retry with dead cookies.
- **Decision:** Explicitly clear authentication cookies when a refresh token is expired or not found, preventing client-side infinite refresh loops.
- **Consequences:**
  - Immediate, clean transition to logged-out state in client UI.

## ADR-012: Active Session Partial Indexing & Opportunistic Token Pruning

- **Status:** Accepted
- **Context:** Revoked refresh tokens accumulate over time, degrading query performance on active sessions.
- **Decision:** Add partial index `CREATE INDEX idx_refresh_tokens_active_user ON refresh_tokens (user_id) WHERE revoked_at IS NULL;` and prune tokens older than 30 days during login operations.
- **Consequences:**
  - Index-only scans for active session operations.
  - Constant-bounded table size without requiring external cron daemons.

## ADR-013: Indian Standard Time (`Asia/Kolkata`) Date Anchor

- **Status:** Accepted
- **Context:** `Assignment.md` mandates that glucose readings cannot be entered for dates in the future. In cloud environments where server clocks run in UTC, a patient entering readings late in the evening (e.g. 11:30 PM IST / 18:00 UTC) or early morning (e.g. 1:00 AM IST / 19:30 UTC previous day) would face date mismatch errors or invalid future rejections.
- **Decision:** Anchor all calendar date boundary calculations to Indian Standard Time (`Asia/Kolkata`, UTC+5:30) using `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Kolkata' })`.
- **Consequences:**
  - Guarantees predictable calendar boundaries across local development, Docker, and UTC-hosted cloud containers.
  - Correctly evaluates today vs. tomorrow regardless of server host timezone.

## ADR-014: Multi-Tenant IDOR Prevention via Strict Parameterized Scoping

- **Status:** Accepted
- **Context:** In multi-tenant healthcare software, Insecure Direct Object Reference (IDOR) vulnerabilities allow malicious users to view, tamper with, or delete other patients' medical records by guessing or altering numerical IDs in URL paths.
- **Decision:** Every read, update, and delete SQL operation on the `readings` table includes `WHERE user_id = $userId` derived exclusively from the verified JWT access cookie. Unmatched requests return `404 Not Found` rather than `403 Forbidden` to prevent information leakage regarding the existence of records belonging to other tenants.
- **Consequences:**
  - Zero leakage of foreign health records.
  - Complete mitigation of IDOR attacks.

## ADR-015: Self-Exclusion on Reading Updates to Prevent False Conflict Rejections

- **Status:** Accepted
- **Context:** When a patient logs all 4 daily readings and subsequently updates a reading on that date (e.g., correcting an error in value or slot via `PUT` or `PATCH`), naive validation checks for daily count (`COUNT >= 4`) or existing slot would flag a false conflict with the reading itself.
- **Decision:** All update queries explicitly exclude the record being edited (`AND id != $id`), ensuring idempotent updates and error corrections on fully populated days succeed seamlessly.
- **Consequences:**
  - Eliminates frustrating false rejections for patients correcting logs.
  - Preserves integrity of the 4 readings/day maximum and single reading/slot constraints.

## ADR-016: Raw String `DATE` Column Parsing (Type OID 1082)

- **Status:** Accepted
- **Context:** Node-postgres (`pg`) by default parses PostgreSQL `DATE` types into JavaScript `Date` objects instantiated at local midnight. When serialized via JSON or `.toISOString()`, the timestamp undergoes timezone conversion, frequently shifting the date backwards by 1 day (e.g. `2026-10-15` turning into `2026-10-14T18:30:00.000Z`).
- **Decision:** Configure `pg.types.setTypeParser(1082, (val) => val)` globally so node-postgres returns pure ISO date strings (`YYYY-MM-DD`).
- **Consequences:**
  - Completely eliminates 1-day date shift anomalies.
  - Preserves date immutability from database to client without manual timezone conversions.

## ADR-017: Explicit Route Parameter Numerical and 64-bit Integer Bounds Validation

- **Status:** Accepted
- **Context:** Route parameters such as `/api/readings/:id` are passed into SQL queries parameterized against PostgreSQL `BIGINT` columns. If an arbitrary non-numeric string (`/api/readings/abc`), negative integer, or integer exceeding 64-bit signed bounds is provided, PostgreSQL throws `22P02` (invalid input syntax for bigint) or `22003` (numeric value out of range), crashing request execution with unhandled 500 errors and leaking SQL statements.
- **Decision:** Enforce `isValidId(id)` validation before executing database queries across all ID-dependent controllers (`getReadingById`, `updateReading`, `patchReading`, `deleteReading`). If invalid, return `404 Not Found: { "error": "Reading not found" }` immediately. In addition, `errorHandler.js` defensively maps `22P02`, `22008`, and `22003` error codes to HTTP 400.
- **Consequences:**
  - Prevents 500 crashes and information leakage from invalid route params.
  - Aligns with REST convention: non-existent/invalid resource IDs cleanly return 404.

## ADR-018: Query Calendar Date Preprocessing & Whitespace Normalization

- **Status:** Accepted
- **Context:** Query parameters in `GET /api/readings?date=...` could accept invalid calendar strings matching regex patterns (e.g. `2026-02-31`), which triggered PostgreSQL datetime overflow errors (`22008`). Additionally, empty string query parameters (`?date=&page=&limit=`) from cleared frontend inputs caused 422 schema rejections.
- **Decision:** Use Zod `.preprocess()` to convert empty query strings to `undefined` for fallback to pagination defaults, and enforce `isValidDateString` calendar validation. In `glucoseValueSchema`, treat whitespace-only values (`"   "`) as missing values returning `"Please enter a glucose value."`.
- **Consequences:**
  - Robust handling of cleared form inputs and invalid calendar dates.
  - Perfect verbatim parity with clinical validation rules in `Assignment.md`.

## ADR-019: Deterministic Report Calendar Math, Hybrid SQL Aggregation, and Prototype Getter Shadowing

- **Status:** Accepted
- **Context:** The reporting requirements mandate three report timeframes:
  1. `daily`: lists all readings in chronological circadian order (`morning_fasting` → `after_breakfast` → `after_lunch` → `after_dinner`) alongside summary statistics.
  2. `month_to_date`: aggregates from the 1st day of the selected date's month to the selected date.
  3. `monthly`: aggregates the whole previous calendar month.
  
  This introduced several technical challenges:
  - Previous month calculations must deterministically handle leap years (February 29 in 2024 vs February 28 in 2025) and year boundaries (January rolling back to December of the previous year).
  - Division by zero and NaN errors when aggregating 0 readings (`count === 0`).
  - In Express, `req.query` is configured with a prototype getter (`defineGetter(req, 'query', ...)`), causing direct assignment (`req[source] = parsed`) in validation middleware to silently fail or fail to mutate `req.query`, preventing Zod default date values from attaching.
  - SQL aggregate dialects: While PostgreSQL supports `ROUND(AVG(value)::numeric, 1)`, mock environments like `pg-mem` lack two-argument `round(float, integer)` implementations, causing test failures.
- **Decision:**
  1. **Deterministic Calendar Range Calculation:** Implement `getReportDateRange(type, dateStr)` using UTC date math (`new Date(Date.UTC(prevYear, prevMonth, 0)).getUTCDate()`), providing mathematically exact boundary resolution without timezone offset shifts.
  2. **Multi-Tenant Parameterized Aggregation:** Execute a single aggregation query strictly scoped by user ID:
     ```sql
     SELECT 
       COUNT(*)::int AS count,
       MAX(value)::int AS highest,
       MIN(value)::int AS lowest,
       AVG(value)::float AS average
     FROM readings
     WHERE user_id = $1 AND date >= $2 AND date <= $3;
     ```
  3. **Arithmetic Rounding & Empty State Parity:** Round `average` in the controller using standard arithmetic rounding to 1 decimal place (`Math.round(val * 10) / 10`). When `count === 0`, return `stats: { count: 0, highest: null, lowest: null, average: null }, readings: []` without division-by-zero crashes.
  4. **Circadian Slot Ordering:** Daily slot readings are ordered chronologically via SQL `CASE slot WHEN 'morning_fasting' THEN 1 WHEN 'after_breakfast' THEN 2 WHEN 'after_lunch' THEN 3 WHEN 'after_dinner' THEN 4 ELSE 5 END ASC`.
  5. **Validation Middleware Getter Shadowing:** Update `validate(schema, source)` to use `Object.defineProperty(req, source, { value: parsed, writable: true, configurable: true, enumerable: true })`, cleanly shadowing Express prototype getters and ensuring transformed/defaulted Zod outputs are accessible on `req.query`.
- **Consequences:**
  - Guaranteed boundary correctness across all calendar edge cases (leap years, year rollovers).
  - 100% dialect portability across local PostgreSQL Docker containers, Supabase, and test mock engines (`pg-mem`).
  - Robust multi-tenant IDOR protection and complete parity with clinical reporting specifications.
