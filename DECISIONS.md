# 📋 Sweety – Architectural Decision Records (ADRs)

This document records the architectural and technical decisions made for the Sweety project, along with context, alternatives considered, and consequences.

---

## ADR-001: Password Hashing with Argon2id

- **Status:** Accepted
- **Context:** `Assignment.md` mentioned bcrypt for password hashing. However, modern cryptographic standards (OWASP, IETF RFC 9106) recognize Argon2id as superior due to memory-hardness that defends against GPU/ASIC acceleration, and resistance to side-channel timing attacks.
- **Decision:** Use `argon2` (Argon2id profile) for all user password hashing and verification.
- **Consequences:**
  - Dramatically improves resistance against offline brute force attacks if database credentials are breached.
  - Requires native bindings (`node-addon-api`/`node-gyp-build`), which are available and tested for modern Node runtimes.

## ADR-002: httpOnly Cookies + Opaque Refresh Token Rotation vs localStorage

- **Status:** Accepted
- **Context:** Storing JWT tokens in browser `localStorage` or `sessionStorage` exposes tokens to Cross-Site Scripting (XSS) exfiltration. Returning tokens in JSON response bodies encourages unsafe frontend storage.
- **Decision:**
  1. Access tokens are stored solely in short-lived (10-minute) `httpOnly`, `Secure` (in production), `SameSite=Lax` cookies.
  2. Tokens are never returned in JSON response bodies.
  3. Refresh tokens are 256-bit opaque random hex strings stored in an `httpOnly` cookie.
  4. Only SHA-256 hashes of refresh tokens are stored in the database.
  5. Tokens are rotated on every exchange (`/api/auth/refresh`). If an already-revoked refresh token is presented, all sessions for that user are immediately revoked (Reuse Detection).
- **Consequences:**
  - Eliminates token theft via XSS.
  - Requires CSRF defense because browser cookies are ambient credentials sent automatically.

## ADR-003: Double Submit Cookie Pattern for CSRF Protection

- **Status:** Accepted
- **Context:** Because authentication relies on cookies, state-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) are susceptible to Cross-Site Request Forgery unless defended.
- **Decision:** Implement the Double Submit Cookie pattern:
  - An accessible `csrfToken` cookie is issued to the client.
  - Any mutating request must pass the matching value in the `X-CSRF-Token` HTTP header.
  - State-changing requests without a valid matching header are rejected with `403 Forbidden: "Invalid or missing CSRF token"`.
- **Consequences:**
  - Third-party domains cannot read the CSRF cookie due to the Same-Origin Policy and cannot construct the custom header.
  - Frontend client must attach the header to mutation requests.

## ADR-004: Primary Keys using `BIGINT GENERATED BY DEFAULT AS IDENTITY`

- **Status:** Accepted
- **Context:** PostgreSQL legacy `SERIAL` types create implicit sequences with quirks and are deprecated in SQL:2003 standards. Supabase and modern PostgreSQL standards recommend `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- **Decision:** Use `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` across all tables (`users`, `refresh_tokens`, `readings`).
- **Consequences:**
  - Full compatibility between local PostgreSQL Docker containers and Supabase.
  - Prevents integer overflow issues that affect standard 32-bit `SERIAL` IDs.

## ADR-005: Strict JWT Claim Verification

- **Status:** Accepted
- **Context:** Misconfigured JWT libraries can accept unsigned tokens (`algorithm: "none"`) or tokens minted by other services if claims are not strictly validated.
- **Decision:**
  - Token signing explicitly specifies `algorithm: 'HS256'`, `issuer: 'sweety-api'`, `audience: 'sweety-client'`, and `expiresIn: '10m'`.
  - Token verification strictly enforces `algorithms: ['HS256']`, `issuer: 'sweety-api'`, `audience: 'sweety-client'`.
- **Consequences:**
  - Completely eliminates algorithm switching and issuer spoofing attacks.

## ADR-006: Zod Boundary Validation

- **Status:** Accepted
- **Context:** Hand-crafted validation in Express controllers is error-prone, violates DRY, and leaks inconsistent error schemas.
- **Decision:** Use Zod schemas with a reusable Express middleware `validate(schema)` that inspects `req.body`, `req.query`, and `req.params`.
- **Consequences:**
  - Clear contract definitions for input payloads.
  - Exact verbatim error message enforcement matching assignment requirements.

---

## ADR-007: Port-Free Test Architecture via Supertest & App Export

- **Status:** Accepted
- **Context:** Binding Express directly to a network port during tests causes port collisions in parallel runs and slow teardown.
- **Decision:** Export `app` from `src/app.js` and isolate network listening in `src/server.js`. Tests invoke `supertest(app)`.
- **Consequences:**
  - Fast, reliable, port-free test execution.
  - Easy environment isolation during CI/CD.

## ADR-008: Atomic Refresh Token Rotation & Concurrency Defense

- **Status:** Accepted
- **Context:** Concurrent calls to `/api/auth/refresh` using the same valid refresh token could read `revoked_at IS NULL` simultaneously, resulting in double token issuance and bypassing breach detection.
- **Decision:** Revoke the refresh token atomically via `UPDATE refresh_tokens SET revoked_at = CURRENT_TIMESTAMP, replaced_by_token_hash = $1 WHERE id = $2 AND revoked_at IS NULL RETURNING id;`. If `rowCount === 0`, concurrent reuse is immediately flagged, triggering emergency revocation of all user sessions.
- **Consequences:**
  - Eliminates token proliferation and race-condition vulnerabilities.
  - Guarantees strictly linear token lineages.

## ADR-009: RFC 6265bis Cookie Clearance Policy

- **Status:** Accepted
- **Context:** RFC 6265bis mandates that cookies set with the `Secure` flag must also include the `Secure` flag when being cleared. Omitting flags causes browsers to ignore `Set-Cookie: token=; Path=/; Expires=Thu, 01 Jan 1970` directives.
- **Decision:** Define explicit cookie clearance constants matching the `path`, `secure`, and `sameSite` parameters used during cookie issuance.
- **Consequences:**
  - Guarantees reliable session termination across modern browser engines.

## ADR-010: Reverse Proxy Trust Configuration for Accurate Rate Limiting

- **Status:** Accepted
- **Context:** When running inside Docker containers or behind reverse proxies (Nginx, cloud load balancers), Express reads client IP from the direct TCP connection (the internal gateway IP), causing all users to share a single rate limiter bucket and risking denial of service.
- **Decision:** Configure `app.set('trust proxy', 1)` when in production or when `TRUST_PROXY` is enabled.
- **Consequences:**
  - Accurately tracks per-client IPs via `X-Forwarded-For`.
  - Prevents benign users from being blocked by neighbors behind proxies.

## ADR-011: Client Cookie Invalidation on Expired Refresh Tokens

- **Status:** Accepted
- **Context:** When `/api/auth/refresh` received an expired refresh token, it returned `401 Unauthorized` without calling `clearAuthCookies()`, causing clients to repeatedly retry with dead cookies.
- **Decision:** Explicitly clear authentication cookies when a refresh token is expired or not found, preventing client-side infinite refresh loops.
- **Consequences:**
  - Immediate, clean transition to logged-out state in client UI.

---

## ADR-012: Active Session Partial Indexing & Opportunistic Token Pruning

- **Status:** Accepted
- **Context:** Revoked refresh tokens accumulate over time, degrading query performance on active sessions.
- **Decision:** Add partial index `CREATE INDEX idx_refresh_tokens_active_user ON refresh_tokens (user_id) WHERE revoked_at IS NULL;` and prune tokens older than 30 days during login operations.
- **Consequences:**
  - Index-only scans for active session operations.
  - Constant-bounded table size without requiring external cron daemons.
