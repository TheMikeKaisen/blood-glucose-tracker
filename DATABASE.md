# 🗄️ Sweety – Database Design & Schema Specification

This document details the relational PostgreSQL database schema, data integrity constraints, indexing strategies, and migration architecture for Sweety.

---

## 1. Connection Architecture

- **Engine:** PostgreSQL 16
- **Driver:** `pg` (`pg.Pool` connection pool singleton)
- **Local Dev:** Managed via Docker Compose (`postgres:16-alpine`)
- **Cloud Readiness:** Seamless migration to Supabase by swapping `DATABASE_URL` in `.env`
- **Integrity Rule:** All queries are strictly parameterized using `$1, $2, ...` placeholders. String concatenation in queries is prohibited.
- **Date Column Type Parsing:** Node-postgres `DATE` parsing (type OID 1082) is configured via `types.setTypeParser(1082, (val) => val)` to return raw ISO `YYYY-MM-DD` strings, preventing local timezone offset shifts across UTC midnight.

## 2. Table Specifications

### 2.1 Table: `users`
Stores registered patient accounts.

```sql
CREATE TABLE IF NOT EXISTS users (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- Case-insensitive unique constraint and index on email
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_email_lower ON users (LOWER(email));
```

#### Column Details
| Column | Type | Nullable | Default | Description |
|---|---|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | Auto | Primary key, 64-bit integer |
| `name` | `VARCHAR(100)` | No | - | Patient's full name (2–100 characters) |
| `email` | `VARCHAR(255)` | No | - | Unique login email (stored normalized lowercase) |
| `password_hash`| `VARCHAR(255)` | No | - | Argon2id cryptographic hash |
| `created_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Account creation timestamp |
| `updated_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Account modification timestamp |

### 2.2 Table: `refresh_tokens`
Maintains hashed refresh tokens for session rotation, revocation, and reuse detection.

```sql
CREATE TABLE IF NOT EXISTS refresh_tokens (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash VARCHAR(64) NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL,
  created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
  revoked_at TIMESTAMPTZ,
  replaced_by_token_hash VARCHAR(64)
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_refresh_tokens_hash ON refresh_tokens (token_hash);
CREATE INDEX IF NOT EXISTS idx_refresh_tokens_user_id ON refresh_tokens (user_id);
-- Partial index for active session lookups per Supabase/PostgreSQL best practices
CREATE INDEX IF NOT EXISTS idx_refresh_tokens_active_user ON refresh_tokens (user_id) WHERE revoked_at IS NULL;
```

#### Pruning & Retention Policy
- Old revoked and expired refresh tokens are opportunistically purged (`expires_at < CURRENT_TIMESTAMP - INTERVAL '30 days'`) during user authentication to prevent table bloat.

CREATE UNIQUE INDEX IF NOT EXISTS idx_refresh_tokens_hash ON refresh_tokens (token_hash);
CREATE INDEX IF NOT EXISTS idx_refresh_tokens_user_id ON refresh_tokens (user_id);
```

#### Column Details
| Column | Type | Nullable | Default | Description |
|---|---|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | Auto | Primary key |
| `user_id` | `BIGINT` | No | - | Foreign key referencing `users(id)` |
| `token_hash` | `VARCHAR(64)` | No | - | SHA-256 hex digest of the 256-bit opaque refresh token |
| `expires_at` | `TIMESTAMPTZ` | No | - | Expiration timestamp (e.g., +7 days) |
| `created_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Issuance timestamp |
| `revoked_at` | `TIMESTAMPTZ` | Yes | `NULL` | Timestamp when revoked during rotation or logout |
| `replaced_by_token_hash` | `VARCHAR(64)` | Yes | `NULL` | SHA-256 hash of the successor token issued during rotation |

### 2.3 Table: `readings` (Implemented in Phase 2)
Stores blood glucose records for patients with clinical constraints and multi-tenancy.

```sql
DO $$ BEGIN
  CREATE TYPE time_slot AS ENUM (
    'morning_fasting',
    'after_breakfast',
    'after_lunch',
    'after_dinner'
  );
EXCEPTION
  WHEN duplicate_object THEN null;
END $$;

CREATE TABLE IF NOT EXISTS readings (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  date DATE NOT NULL,
  slot time_slot NOT NULL,
  value INTEGER NOT NULL CHECK (value >= 40 AND value <= 600),
  created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT uq_user_date_slot UNIQUE (user_id, date, slot)
);

CREATE INDEX IF NOT EXISTS idx_readings_user_date ON readings (user_id, date);
CREATE INDEX IF NOT EXISTS idx_readings_user_pagination ON readings (user_id, date DESC, slot ASC);
```

#### Column Details
| Column | Type | Nullable | Default | Description |
|---|---|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | Auto | Primary key, 64-bit integer |
| `user_id` | `BIGINT` | No | - | Foreign key referencing `users(id)` |
| `date` | `DATE` | No | - | Calendar date of reading (ISO `YYYY-MM-DD`) |
| `slot` | `time_slot` | No | - | ENUM (`morning_fasting`, `after_breakfast`, `after_lunch`, `after_dinner`) |
| `value` | `INTEGER` | No | - | Whole glucose measurement in mg/dL (bounded 40–600) |
| `created_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Row creation timestamp |
| `updated_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Row last modified timestamp |

#### Constraints & Business Rules Enforced
- **`uq_user_date_slot`**: Guarantees uniqueness for `(user_id, date, slot)` preventing duplicate readings per slot per day, even under concurrent write conditions.
- **`CHECK (value >= 40 AND value <= 600)`**: Database-level check constraint defending against physiological impossibilities.
- **`ON DELETE CASCADE`**: Automatically purges readings when a user account is deleted.

#### Index Optimization for Reports & Analytics
- **`idx_readings_user_date` (`user_id, date`)**: Perfectly satisfies both equality and range predicates executed by `GET /api/reports` (`WHERE user_id = $1 AND date >= $2 AND date <= $3`). PostgreSQL leverages B-tree index range scans directly filtering by user before evaluating aggregate functions (`COUNT`, `MAX`, `MIN`, `AVG`), preventing full-table sequential scans.
- **`idx_readings_user_pagination` (`user_id, date DESC, slot ASC`)**: Optimizes paginated history queries and chronological order sorting.

## 3. Migration Runner

Database migrations are executed via `server/src/db/migrate.js`:
- Reads and parses `server/src/db/schema.sql`.
- Executes DDL transactions against the active PostgreSQL database.
- Executed via npm script: `npm run db:migrate`.
- Can be run manually or during container bootstrap.
